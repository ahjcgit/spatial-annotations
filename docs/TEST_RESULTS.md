## Android emulator runtime

A headless Android API 30 Google APIs x86_64 emulator was launched with KVM in a local Docker test container. This is **not RayNeo firmware**.

The default APK installed and `.MainActivity` launched. The UIAutomator script [android_smoke.py](../scripts/android_smoke.py), using live backend data generated by `e2e.py`, exercised:

1. Alice login to the real LAN backend.
2. Explicit **SIMULATION** lookup of object A, retrieving public/private/group notes.
3. Public annotation creation through the Android UI and retrieval of the new note.
4. App process restart, verifying Android Keystore-backed session recovery.
5. Sign-out and Bob login, retrieving public/group/new public notes without Alice's private content.
6. Guest transition, runtime CAMERA permission, Camera2 virtual-scene stream startup and explicit stop.

[Run log](evidence/android-smoke.log); screenshots: [Alice](android-alice.png), [Bob](android-bob.png). The script uses manual marker input; it does **not** optically scan a marker in the emulator camera. QR pixel decoding and camera acquisition are separately verified components. The test harness needed adjustments for Android system UI/launcher behavior during setup; the completed application workflow is the evidence reported above.

To reproduce on an already running disposable emulator with the APK installed:

```bash
.venv/bin/pip install -r scripts/requirements-device.txt
.venv/bin/python scripts/e2e.py --url http://YOUR_SERVER_LAN_IP:8000 --output demo-data.json
.venv/bin/python scripts/android_smoke.py --serial emulator-5554 --data demo-data.json
```

Use a **fresh** E2E dataset for each script run (the Android test adds one note and checks exact counts). It signs in/out, creates test data and captures screenshots. It does not erase or reset the emulator. Android display density 240 was used on a 1080×1920 emulator to keep controls visible. Read the script before running against a personal device; the intended target is a disposable emulator.
